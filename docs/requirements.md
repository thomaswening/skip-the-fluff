## Requirement conventions
**SHALL** = mandatory for the stated release; **SHOULD** = preferred, with an acceptable documented exception; **COULD** = optional or future capability. Each requirement has a stable ID and is never renumbered. Conditions are expressed as **WHEN … THEN …**, **IF … THEN …**, **BEFORE …**, **WHILE …** or **AFTER …**. An implementation technique is not a product requirement unless explicitly stated. Items marked **OPEN** require a decision before they can be treated as acceptance criteria. **OUT OF SCOPE** marks a capability explicitly not required for the first release.

**The website** = Duolingo's web application at duolingo.com and its subdomains (such as support.duolingo.com), as served to a mobile browser. Skip the Fluff displays it; it does not own, copy or modify it.

**Fix** (used by [section 2](#2-distraction-removal), [REQ-018](#req-018) and [section 8](#8-maintainability)): one change Skip the Fluff applies to the website on the user's device, such as hiding an element or pressing a skip control, that implements one requirement. Each fix can be switched off on its own.

**Disputed fix** (used by [REQ-001](#req-001) and [REQ-018](#req-018)): a fix that removes a screen which other learners may reasonably find useful, even though Thomas does not. Whether a fix is disputed is stated in its requirement when the requirement is written.

**Exercise** = a screen of a lesson on which the learner answers something. **Non-exercise screen** = any other screen in or around a lesson: intros, vocabulary previews, celebrations, animations, prompts and promotions. The distinction is what [REQ-012](#req-012) relies on.

**Reference device** (used by [REQ-009](#req-009), [REQ-013](#req-013), [REQ-014](#req-014), [REQ-022](#req-022) and [REQ-034](#req-034)): Thomas's Samsung Galaxy S25 FE, in portrait orientation, with Chrome's current [WebView](glossary.md#webview).

## 1. Purpose and users

<a id="req-001"></a>**REQ-001 — Purpose (SHALL).** Skip the Fluff SHALL let a learner do Duolingo lessons on an Android phone through the website, with the screens that do not serve learning removed, so that a session takes little more time than its exercises do. It serves (a) Thomas, doing a short session before work, and (b) other Duolingo learners who install it from GitHub. Thomas's use decides which fixes exist. WHEN a fix serves Thomas but other learners may want to keep the screen it removes, THEN it is a [disputed fix](#requirement-conventions) and ships switched off ([REQ-018](#req-018)). Decided by Thomas, 8 November 2026. Rationale: the official Android app shows many motivational and gamification screens around each lesson; they break the flow and cost time, and Duolingo has not acted on repeated feedback asking for a setting to skip them.

<a id="req-002"></a>**REQ-002 — Installing without developer tools (SHALL).** A learner SHALL be able to install and use Skip the Fluff on an unrooted Android phone by downloading one [APK](glossary.md#apk), without a computer, ADB, root or developer options.

<a id="req-003"></a>**REQ-003 — Out of scope (OUT OF SCOPE).** The following are out of scope for every release, not only the first: completing, answering or skipping exercises; earning or changing XP, gems, streaks or other rewards; unlocking paid (Super or Max) features; modifying, decompiling or patching Duolingo's Android app; distribution through the Google Play Store ([REQ-028](#req-028)); iOS. Rationale: each would turn a display tool into one that cheats, circumvents payment or breaks Duolingo's terms of service, and so puts users' accounts and the project at risk.

<a id="req-004"></a>**REQ-004 — The website, not the app (SHALL).** Skip the Fluff SHALL work by displaying the website and SHALL NOT read, modify or depend on Duolingo's Android app. Rationale: Duolingo's terms forbid reverse engineering its apps, and a modified app can be detected by signature checks and the Play Integrity API; the website needs neither.

## 2. Distraction removal

None of the fixes in this section is a [disputed fix](#requirement-conventions) unless its requirement says so. [REQ-034](#req-034) says how each of them is accepted.

<a id="req-034"></a>**REQ-034 — Accepting a fix (SHALL).** A fix of this section SHALL count as working when, on the reference device, the screen it removes is not shown on 5 consecutive occasions on which the website would have shown it, and the learner can carry on each time as if they had closed it themselves. A requirement with its own Measurement line, such as [REQ-009](#req-009), is accepted by that line instead. The acceptance holds for the website as it was when the fix was last verified. AFTER Duolingo changes the website so that a fix no longer matches, [REQ-025](#req-025) governs until the fix is repaired. Rationale: without an acceptance line, "SHALL NOT display it" could be read as a promise about every future version of the website, which no release can keep. The count of 5 matches [REQ-009](#req-009) and [REQ-014](#req-014). Decided by Thomas, 8 November 2026.

<a id="req-005"></a>**REQ-005 — "Use the app" prompts (SHALL).** WHEN the website shows a prompt to install or switch to Duolingo's app, THEN Skip the Fluff SHALL NOT display it. Rationale: in a mobile browser the prompt appears after every session and every time the user returns to the browser (observed by Thomas, 8 November 2026).

<a id="req-006"></a>**REQ-006 — Leaderboard and league popups (SHALL).** WHEN the website shows a leaderboard or league popup, THEN Skip the Fluff SHALL NOT display it.

<a id="req-007"></a>**REQ-007 — Streak and reminder nags (SHALL).** WHEN the website shows a screen or popup whose purpose is to encourage keeping a streak or to set up reminders, THEN Skip the Fluff SHALL NOT display it.

<a id="req-008"></a>**REQ-008 — Super and Max upsells (SHALL).** WHEN the website shows an advertisement or promotion for Super or Max, THEN Skip the Fluff SHALL NOT display it. It SHALL NOT unlock or imitate any paid feature ([REQ-003](#req-003)). The screen shown when the learner runs out of hearts is not an upsell in this sense: it offers choices the learner must make (refill with gems, practise to earn hearts, quit), so Skip the Fluff SHALL show it unchanged, its Super option included. Decided by Thomas, 8 November 2026.

<a id="req-009"></a>**REQ-009 — Unit-completion animation (SHALL).** WHEN the learner completes a unit, THEN the learner SHALL be able to continue within 1 second of the completion animation appearing. Measurement: on the reference device, from the first frame of the animation to the next screen being shown or a continue control being usable, over 5 unit completions; every one within 1 second. Threshold decided by Thomas, 8 November 2026 ([OPEN-F](#open-f)).

<a id="req-010"></a>**REQ-010 — Listening-lesson intro (SHALL).** WHEN a listening lesson starts, THEN the first screen the learner sees SHALL be its first exercise. Neither the intro (which the website already lets the learner skip) nor the ["important words" preview](glossary.md#important-words-preview) SHALL be shown. The **"important words" preview** is the screen before the first exercise that lists the lesson's new words and plays them as audio. It is not the exercise in which the learner matches audio snippets to their translations: that is an exercise, and [REQ-012](#req-012) forbids touching it. Clarified by Thomas, 8 November 2026.

<a id="req-011"></a>**REQ-011 — Further distractions (SHOULD).** Further non-exercise screens that Thomas identifies from screenshots taken during use SHOULD be removed. Each one becomes its own requirement in this section before it is implemented, stating whether it is a [disputed fix](#requirement-conventions). **[OPEN-A](#open-a):** which screens.

<a id="req-012"></a>**REQ-012 — Acting only on non-exercise screens (SHALL).** To remove a non-exercise screen, Skip the Fluff SHALL hide it wherever hiding alone lets the learner continue. Only where hiding would leave the lesson stuck MAY it press the website's own skip, continue or close control on that screen. It SHALL NOT press a control that changes a setting, buys anything or subscribes to anything. It SHALL NOT interact with an exercise in any way. IF a screen cannot be identified with confidence as a non-exercise screen, THEN Skip the Fluff SHALL leave it displayed and SHALL NOT act on it. Actions the learner takes, such as the back gesture of [REQ-037](#req-037), are the learner's own and not covered by this requirement. Rationale: pressing a control on the wrong screen could answer or skip an exercise, which [REQ-003](#req-003) excludes; showing a distraction is the cheaper failure. Hiding comes first because Duolingo's terms forbid accessing the service by automated means: hiding changes only what the phone shows, while pressing a control acts on the service for the learner. Decided by Thomas in the intake conversation and confirmed in the first elicitation pass, 8 November 2026; hiding first decided by Thomas in the second pass, 8 November 2026.

## 3. Display and lesson flow

<a id="req-013"></a>**REQ-013 — Using the whole screen (SHALL).** Skip the Fluff SHALL show the website without any browser interface (address bar, tabs, toolbars). WHILE a lesson is shown, Android's status and navigation bars SHALL be hidden; outside a lesson they SHALL be shown. WHILE a lesson is shown on the reference device, all of an exercise, including its check or continue button, SHALL be visible without scrolling. This behaviour SHALL NOT have a switch in settings ([REQ-018](#req-018)). Rationale: in Chrome on the reference device, lesson content does not fit vertically (observed by Thomas, 8 November 2026); outside lessons the clock and normal navigation are more useful than the extra height. System bars and the missing switch decided by Thomas, 8 November 2026 ([OPEN-C](#open-c)).

<a id="req-045"></a>**REQ-045 — Screen orientation (SHALL).** Skip the Fluff SHALL allow the orientations the website allows in Chrome on the reference device. IF the website can be used in landscape there, THEN Skip the Fluff SHALL follow Android's auto-rotate setting; otherwise it SHALL stay in portrait. The promise of [REQ-013](#req-013) that an exercise fits without scrolling holds in portrait only. Decided by Thomas, 8 November 2026. **[OPEN-H](#open-h):** whether the website can be used in landscape.

<a id="req-014"></a>**REQ-014 — The lesson survives an app switch (SHALL).** WHEN the learner leaves Skip the Fluff during a lesson and returns within 5 minutes, THEN the lesson SHALL continue at the exercise the learner left. Measurement: on the reference device, start a lesson, answer two exercises, switch to another app for 4 minutes, return; repeated 5 times, the lesson continues every time. This behaviour SHALL NOT have a switch in settings ([REQ-018](#req-018)). Note: Android may end a background app under memory pressure; this requirement covers ordinary short switches. Rationale: in Chrome, switching to ChatGPT to ask why an answer was wrong cancels the lesson (observed by Thomas, 8 November 2026). The 5-minute window and the missing switch were confirmed by Thomas, 8 November 2026 ([OPEN-C](#open-c)).

<a id="req-015"></a>**REQ-015 — Pages outside the website (SHALL).** WHEN the learner navigates to a page on a host that is not part of the website, THEN that page SHALL open in the phone's default browser, not inside Skip the Fluff. Images, audio, scripts and other resources the website loads from other hosts are not affected. WHEN the website starts a sign-in with Google, Facebook or Apple, THEN that sign-in SHALL also open in the default browser, until [OPEN-B](#open-b) is decided. It does not sign the learner in to Skip the Fluff. Rationale: a third-party page inside the app would be outside the scope of the fixes and could break [REQ-020](#req-020) and [REQ-021](#req-021); Google rejects sign-in inside a WebView anyway. Scope and level decided by Thomas, 8 November 2026.

<a id="req-037"></a>**REQ-037 — The back gesture (SHALL).** WHEN the learner uses Android's back gesture or back button, THEN Skip the Fluff SHALL go back one page in the website's history. WHILE a lesson is shown, the back gesture SHALL NOT end the lesson unless the learner confirms it, as the website's own close control asks them to. On the learning path, the page the website shows after sign-in, the back gesture SHALL close the app. Decided by Thomas, 8 November 2026.

<a id="req-038"></a>**REQ-038 — Microphone and audio (SHALL).** WHEN the website asks for the microphone, THEN Skip the Fluff SHALL ask for Android's microphone permission if it has not been granted yet, and SHALL pass the learner's answer to the website. Audio SHALL play as it does in Chrome, without an extra tap. IF the learner refuses the microphone, THEN the website's own option to skip speaking exercises for now remains available; Skip the Fluff SHALL NOT use it on the learner's behalf ([REQ-012](#req-012)). Acceptance: on the reference device, a speaking exercise records the learner's voice and a listening exercise plays its audio by itself, as in Chrome. Rationale: a WebView grants neither the microphone nor audio without a tap by default, so speaking exercises could not be answered and listening exercises would wait for a tap. Decided by Thomas, 8 November 2026.

<a id="req-044"></a>**REQ-044 — No connection (SHALL).** IF the website cannot be reached, because the phone is offline or duolingo.com does not answer, THEN Skip the Fluff SHALL show its own screen saying so, with a button that tries again, instead of Android's raw error page. It SHALL NOT retry by itself in a loop. The menu button ([REQ-035](#req-035)) SHALL stay available on that screen. Level SHALL decided by Thomas, 8 November 2026, because the screen is small to build.

## 4. Account and sign-in

<a id="req-016"></a>**REQ-016 — Email and password sign-in (SHALL).** The learner SHALL be able to sign in with an email address and password, and SHALL stay signed in across restarts of the app and the phone until they sign out or the website ends the session. Rationale: Google blocks its sign-in inside embedded browsers, so email and password is the sign-in that works in the first release. Decided by Thomas, 8 November 2026.

<a id="req-039"></a>**REQ-039 — Password managers (SHOULD).** Android's autofill, which password managers such as Google Password Manager and Bitwarden use, SHOULD be able to fill in the website's sign-in form. The password manager fills the form directly; Skip the Fluff still SHALL NOT read or store the password ([REQ-021](#req-021)). Acceptance: on the reference device, Google Password Manager offers a saved Duolingo password in the sign-in form and fills it in. Rationale: typing a long password on a phone is where many learners give up. Decided by Thomas, 8 November 2026.

<a id="req-017"></a>**REQ-017 — Google sign-in (COULD).** A later release COULD let the learner sign in with Google. Thomas wants this after the first release (8 November 2026). **[OPEN-B](#open-b):** how.

## 5. Settings and information

<a id="req-035"></a>**REQ-035 — The menu button (SHALL).** Skip the Fluff SHALL show a small button over the website that opens its menu: settings ([REQ-018](#req-018)), about ([REQ-019](#req-019)) and reporting a problem ([REQ-033](#req-033)). On the reference device it SHALL cover no control of the website. WHILE a lesson is shown, the button SHALL be smaller and semi-transparent, placed where the website shows no control, and a tap on it SHALL mark the moment ([REQ-036](#req-036)) instead of opening the menu. Rationale: the website fills the whole screen without browser interface ([REQ-013](#req-013)), so without the button the learner could not reach anything of Skip the Fluff's own. Decided by Thomas, 8 November 2026.

<a id="req-036"></a>**REQ-036 — Marking a problem during a lesson (SHOULD).** WHILE a lesson is shown, one tap on the menu button ([REQ-035](#req-035)) SHOULD mark that something is wrong at this moment, without leaving the lesson and without asking for any input. A brief confirmation SHALL show that the mark was taken. AFTER the lesson, the menu button SHALL show that marks are waiting, without a popup or any other interruption. The learner reports them from the menu ([REQ-033](#req-033)) or dismisses them. A mark SHALL hold only its time and the status of the fixes at that time ([REQ-042](#req-042)), never page content or a screenshot. Rationale: a report is most useful when the problem is seen, but filling it in then would break the lesson. Asked for by Thomas, 8 November 2026.

<a id="req-018"></a>**REQ-018 — Switching fixes on and off (SHALL).** Skip the Fluff SHALL have a settings screen on which the learner can switch each fix of [REQ-005](#req-005) to [REQ-011](#req-011) on or off individually. Every fix SHALL be on by default, except a [disputed fix](#requirement-conventions), which SHALL be off by default ([REQ-001](#req-001)). WHEN the learner leaves the settings screen after a change, THEN Skip the Fluff SHALL reload the website so that the change takes effect. Settings cannot be opened during a lesson ([REQ-035](#req-035)), so the reload never ends one. Full screen ([REQ-013](#req-013)) and keeping the lesson across an app switch ([REQ-014](#req-014)) SHALL NOT have switches. Decided by Thomas, 8 November 2026. Rationale for the reload: the website is a [single-page app](glossary.md#single-page-app) that rarely loads a new page, so a change that waited for the next page load might never take effect. Rationale for the missing switches: those two are why the app exists, not optional fixes, and each switch adds a state to test.

<a id="req-019"></a>**REQ-019 — About and disclaimer (SHALL).** Skip the Fluff SHALL have an about screen stating that it is unofficial, not affiliated with or endorsed by Duolingo, and used at the user's own risk, with its version, licence and a link to its repository.

<a id="req-033"></a>**REQ-033 — Reporting a broken fix from the app (SHOULD).** WHEN the learner meets a distraction that is back or a screen that was wrongly hidden, THEN they SHOULD be able to start a report from inside Skip the Fluff in at most two taps: the menu button ([REQ-035](#req-035)), then "Report a problem". IF Skip the Fluff offers this report, THEN the following hold. By default the report SHALL open as a pre-filled email in the phone's mail app, addressed to the project's report address ([OPEN-J](#open-j)). A learner with a GitHub account SHALL be able to choose a pre-filled new issue in the repository instead, opened in the phone's default browser. In both cases the learner reviews the report, attaches a screenshot if they want and sends it themselves. The report SHALL be pre-filled with the app version, the Android version, the WebView version, the fixes switched on, the status of each fix ([REQ-042](#req-042)) and the marks waiting ([REQ-036](#req-036)). It SHALL NOT include the learner's account name, email address or page content. Skip the Fluff SHALL NOT take or attach a screenshot itself. Before the learner attaches a screenshot, the report SHALL tell them that a screenshot can show their name, profile picture and other learners' names, and ask them to crop or cover those. The issue SHALL also say that it is public. The email SHALL also say that the maintainer reads it, may copy it into a public issue without personal data, and deletes it once the problem is handled. Rationale for email as the default: most learners have no GitHub account (raised by Thomas in his review, 8 November 2026). Rationale for the warning: GitHub issues are public and cannot be made private, so a careless screenshot publishes personal data of the learner and of others (raised by Thomas, 8 November 2026). Rationale for the report itself: a report is most useful right when the problem is seen; opening the mail app or the browser keeps [REQ-020](#req-020), because Skip the Fluff itself sends nothing. Asked for by Thomas, 8 November 2026.

<a id="req-046"></a>**REQ-046 — Emailed reports become issues automatically (COULD).** A later release COULD turn emailed reports ([REQ-033](#req-033)) into issues in the repository without the maintainer copying them by hand. Only the pre-filled part of a report (versions, fixes, fix status, marks) SHALL be published automatically. The sender's address, their own text and attachments SHALL NOT be, because nobody has checked them for personal data. Skip the Fluff itself SHALL still send nothing ([REQ-020](#req-020)). GitHub has no address that accepts reports from anyone: creating an issue needs a token, and a token inside the APK could be extracted by anyone who downloads it. Asked for by Thomas in his review, 8 November 2026. **[OPEN-K](#open-k):** how.

## 6. Privacy and safety

<a id="req-020"></a>**REQ-020 — No data collection (SHALL).** Skip the Fluff SHALL NOT make any network request other than these: those the website itself makes; those Android's WebView makes on its own for the learner's safety, such as [Safe Browsing](glossary.md#safe-browsing); and the update check of [REQ-040](#req-040) once the learner has switched it on. It SHALL NOT contain analytics, tracking, advertising or crash reporting. Safe Browsing kept switched on by Thomas, 8 November 2026.

<a id="req-040"></a>**REQ-040 — Opt-in update check (SHALL).** Skip the Fluff SHALL have a setting "Check for new releases", off until the learner switches it on. On the first start, a one-time dialog SHALL ask whether to switch it on, with neither answer preselected. The dialog SHALL say that GitHub then receives the phone's IP address once a day and that Skip the Fluff itself receives nothing. WHILE the setting is on, Skip the Fluff SHALL ask GitHub at most once a day for the latest release. WHEN a newer release exists, THEN the menu button ([REQ-035](#req-035)) SHALL show it, with a link to the release. Rationale: fixes reach learners only through new releases ([REQ-024](#req-024)). Duolingo changes the website often, so a learner who never hears of a release keeps a broken fix. Under the GDPR an IP address is personal data, so the check rests on the learner's consent, which they must give actively. This is not legal advice. Decided by Thomas, 8 November 2026.

<a id="req-021"></a>**REQ-021 — No access to credentials (SHALL).** Sign-in SHALL happen in the website's own form. Skip the Fluff SHALL NOT read, store or transmit the learner's password.

<a id="req-031"></a>**REQ-031 — Consent and legal notices are left alone (SHALL).** Skip the Fluff SHALL NOT hide, accept, decline or otherwise answer the website's cookie consent banner, privacy notices, terms of service or any other legal notice. No fix ([REQ-005](#req-005) to [REQ-011](#req-011)) SHALL target them, even where they interrupt a lesson. Rationale: under the EU's General Data Protection Regulation (GDPR) and Germany's Telecommunications Digital Services Data Protection Act (TDDDG, § 25), consent to cookies must be given by the user themselves. A tool that answered the banner for them would make that consent invalid, and the project would be responsible. Raised by Thomas's question on European and German data law, 8 November 2026.

## 7. Execution environment

<a id="req-022"></a>**REQ-022 — Supported devices (SHALL).** Skip the Fluff SHALL run on Android phones from a minimum Android version upwards, and SHALL be accepted on the reference device. **[OPEN-D](#open-d):** the minimum version.

<a id="req-048"></a>**REQ-048 — Unsupported WebView (SHALL).** IF at start the phone's [WebView](glossary.md#webview) lacks what the [fixes](glossary.md#fix) need, THEN Skip the Fluff SHALL show its own screen instead of the website. The screen SHALL say what is missing and SHALL have a button that opens the WebView's page in the Play Store. It SHALL say that IF no update is offered, THEN the phone is not supported, and how to uninstall the app. It SHALL NOT offer to continue without fixes. Rationale: Android checks only the Android version when it installs an app; the WebView is a separate app that updates on its own and can change after installation, so only the app itself can check it. Without fixes the app has no purpose. Decided by Thomas, 8 November 2026, while deciding [ADR-0002](adr/0002-fix-engine.md).

<a id="req-029"></a>**REQ-029 — Language (SHALL).** The app's interface, the README and all documentation SHALL be in English. Decided by Thomas, 8 November 2026.

## 8. Maintainability

<a id="req-023"></a>**REQ-023 — Fixes kept apart from the app (SHALL).** Each fix SHALL be defined separately from the rest of the app and SHALL name the requirement it implements. Acceptance: when the website changes, repairing a fix changes only that fix's definition. Rationale: Duolingo can change the website at any time, so fixes are the part that will need repair most often.

<a id="req-024"></a>**REQ-024 — Fixes ship with the app (SHALL).** Fixes SHALL be delivered only inside the installed app, and an updated fix only through a new release. Skip the Fluff SHALL NOT download fixes, rules or code at run time. An APK installed through [REQ-041](#req-041) is a new release, not code downloaded at run time: the learner confirms it and Android checks its signature. Rationale: code downloaded at run time could be altered in transit or at its source without review. Decided by Thomas, 8 November 2026.

<a id="req-025"></a>**REQ-025 — A broken fix fails safe (SHALL).** IF a fix no longer matches the website, THEN Skip the Fluff SHALL show the website unchanged for that fix, SHALL NOT crash, and SHALL NOT block the lesson.

<a id="req-042"></a>**REQ-042 — Fix status (SHOULD).** Skip the Fluff SHOULD record, on the phone only, how many lessons the learner has completed since each fix last took effect, and SHOULD show this on the settings screen, e.g. "leaderboard popup: last hidden 12 lessons ago". Each fix's requirement SHOULD state after how many lessons without effect the fix counts as possibly broken, e.g. 5 for [REQ-005](#req-005), whose prompt appears after every session. WHEN a fix passes that count, THEN the settings screen and the report ([REQ-033](#req-033)) SHOULD flag it as possibly broken. The record SHALL NOT include page content or account data. It SHALL leave the phone only inside a report the learner sends themselves ([REQ-033](#req-033)). Rationale: a fix that has not taken effect for many lessons has probably stopped matching the website ([REQ-025](#req-025)), so the record tells the maintainer which fix to repair first. Lessons are counted instead of days because days without use say nothing about a fix (raised by Thomas in his review, 8 November 2026). Decided by Thomas, 8 November 2026.

## 9. Licence, naming and distribution

<a id="req-026"></a>**REQ-026 — Licence (SHALL).** Skip the Fluff SHALL be released under the GNU General Public License v3.0 only. Rationale: changes others make stay open; the existing unofficial Duolingo desktop wrapper, "DL: language lessons" by hmlendea on Flathub ([hmlendea/dl-desktop](https://github.com/hmlendea/dl-desktop)), uses the same licence and appears to be tolerated by Duolingo. Decided by Thomas, 8 November 2026.

<a id="req-027"></a>**REQ-027 — Name and branding (SHALL).** The product SHALL be named Skip the Fluff. Its name, icon and assets SHALL NOT use Duolingo's name, logo, mascot (including the name "Duo"), owl imagery or brand colours. Duolingo SHALL be mentioned only to describe what the app works with ("an unofficial, distraction-free wrapper for duolingo.com"). The repository is [thomaswening/skip-the-fluff](https://github.com/thomaswening/skip-the-fluff), public from its creation. Rationale: trademark is where a complaint from Duolingo is most likely. Name chosen by Thomas, 8 November 2026; name clearance and visibility in [OPEN-E](#open-e).

<a id="req-028"></a>**REQ-028 — Distribution (SHALL).** The first release SHALL be distributed as a signed APK on the repository's GitHub Releases. Distribution through F-Droid COULD follow ([OPEN-G](#open-g)). Distribution through the Google Play Store is OUT OF SCOPE: Play does not allow apps whose main purpose is to show a website without its owner's permission. Decided by Thomas, 8 November 2026.

<a id="req-043"></a>**REQ-043 — Updates keep sign-in and settings (SHALL).** Every release SHALL be signed with the same [signing key](glossary.md#signing-key) and SHALL install over the previous release without uninstalling it. Sign-in ([REQ-016](#req-016)) and settings ([REQ-018](#req-018), [REQ-040](#req-040)) SHALL survive the update. Acceptance: install release N, sign in, change a setting, install release N+1 over it; the learner is still signed in and the setting is unchanged. How the key is kept safe is for an [ADR](glossary.md#adr). Rationale: Android refuses an update signed with another key, so the learner would have to uninstall first and would lose sign-in and settings. Decided by Thomas, 8 November 2026.

<a id="req-041"></a>**REQ-041 — Installing updates from the app (COULD).** A later release COULD, WHEN the update check ([REQ-040](#req-040)) finds a newer release and the learner confirms, download its APK and hand it to Android to install. Android installs it only if it is signed with the same key ([REQ-043](#req-043)). **[OPEN-I](#open-i):** whether the permission this needs is acceptable. Asked for by Thomas, 8 November 2026.

<a id="req-030"></a>**REQ-030 — README (SHALL).** The repository SHALL have a README that states what Skip the Fluff does and does not do ([REQ-003](#req-003)), how to install it, how to learn of new releases ([REQ-040](#req-040)), the disclaimer of [REQ-019](#req-019), and how to report a fix that has stopped working ([REQ-033](#req-033)), and what happens to the personal data in an emailed report: who reads it, that it is deleted once handled, and that only content without personal data is copied into public issues.

<a id="req-047"></a>**REQ-047 — System requirements stated before installing (SHALL).** The README ([REQ-030](#req-030)), the installation guide ([REQ-032](#req-032)) and every release page SHALL state the minimum Android version ([REQ-022](#req-022)) and the minimum [WebView](glossary.md#webview) version ([REQ-048](#req-048)), and SHALL say how to check and update the phone's WebView. Acceptance: a learner can tell from the release page alone, before downloading the [APK](glossary.md#apk), whether their phone is supported. Rationale: a learner whose phone cannot run the fixes should find out before installing, not after. Decided by Thomas, 8 November 2026, while deciding [ADR-0002](adr/0002-fix-engine.md).

<a id="req-032"></a>**REQ-032 — Installation guide for non-technical users (SHALL).** The first release SHALL come with a step-by-step installation guide, linked from the README, for learners who have never installed an app outside the Play Store. It SHALL cover downloading the APK on the phone, allowing the browser to install apps, the warnings Android and Google Play Protect show, installing an update, and uninstalling, with a screenshot of each screen on the reference device. Acceptance: a person who has never [sideloaded](glossary.md#sideloading) an app installs Skip the Fluff on their own phone using only the guide, without help. The test needs such a volunteer, found before the first release. Rationale: [REQ-002](#req-002) makes installation possible without a computer, but the security warnings on the way are what stop non-technical users. Asked for by Thomas, 8 November 2026.

<a id="open-decisions"></a>
## 10. Deferred capabilities and unresolved decisions

An open decision is resolved immediately before the work that depends on it, not in advance: several are better settled with evidence from a [spike](glossary.md#spike) than by argument, and one settled early on a guess is worse than one settled late on a measurement. The roadmap names, per phase, which decisions that phase needs, and a phase is not complete until they are recorded here. Each decision below therefore carries a **Needed by** note saying what it blocks. A decision stays in this section once settled, marked **Resolved**, so that the reasoning survives the decision.

<a id="open-a"></a>**OPEN-A — Which further distractions to remove.** [REQ-011](#req-011). Thomas will send screenshots of screens to remove as they come up in lessons. Each becomes a requirement in [section 2](#2-distraction-removal). Reported so far, awaiting a screenshot: the puzzle animation and its screen (Thomas, 8 November 2026). The screens after the last exercise of a lesson (lesson summary, streak extended, daily-quest progress, chests, XP-boost and friend-quest offers) get no general rule: each is collected here like any other screen. Decided by Thomas, 8 November 2026. **Needed by:** nothing yet; collected continuously.

<a id="open-b"></a>**OPEN-B — How to support Google sign-in.** [REQ-017](#req-017), [REQ-021](#req-021). Google rejects sign-in from embedded browsers. Candidates: sign in through a [Custom Tab](glossary.md#custom-tab) and hand the session over to the app (works, but the hand-over is fragile and must not violate [REQ-021](#req-021)); ask Google users to add a password to their Duolingo account (no code, but a manual step for users). Until it is decided, a Google sign-in opens in the default browser ([REQ-015](#req-015)). **Needed by:** the first release after 1.0.

<a id="open-c"></a>**OPEN-C — Full-screen details and further switches.** [REQ-013](#req-013), [REQ-014](#req-014), [REQ-018](#req-018). Whether Android's status and navigation bars are hidden during lessons or always, and whether [REQ-013](#req-013) and [REQ-014](#req-014) can be switched off. **Needed by:** the settings design. **Resolved:** the bars are hidden only while a lesson is shown, so that the clock and normal navigation stay available elsewhere. Neither full screen nor keeping the lesson gets a switch: they are why the app exists, and each switch adds a state to test. Accepted by Thomas as proposed, 8 November 2026.

<a id="open-d"></a>**OPEN-D — Minimum Android version.** [REQ-022](#req-022). Lower reaches more phones; higher allows simpler code and newer WebView behaviour. **Needed by:** the ADR on the app's structure and build.

<a id="open-e"></a>**OPEN-E — Name clearance.** [REQ-027](#req-027). A web check by Claude on 8 November 2026 found no app, F-Droid entry or GitHub project named Skip the Fluff, but a YouTube summary channel and a consulting agency use the phrase, and the EUIPO and DPMA registers were not searched. **Needed by:** making the repository public. **Resolved:** a search by Claude in [TMview](https://www.tmdn.org/tmview/) on 8 November 2026, which covers the EUIPO, DPMA, USPTO, UKIPO and most national offices, found no trade mark containing "skip the fluff", "skipthefluff" or "skip fluff" (a control search for "duolingo" returned 101 marks, so the search worked). The closest mark is the single word "Fluff", filed in France on 16 September 2026 for classes 9, 41 and 42 (INPI 5298706); it does not cover the phrase. This is not legal advice. On this evidence Thomas decided, 8 November 2026, to keep the name and create the repository public.

<a id="open-f"></a>**OPEN-F — How fast "without waiting" is.** [REQ-009](#req-009), [REQ-010](#req-010). A measurable threshold for the time from a non-exercise screen appearing to the learner being able to continue. **Needed by:** acceptance of [REQ-009](#req-009). **Resolved:** within 1 second, measured on the reference device as [REQ-009](#req-009) states. One second feels immediate yet leaves time to identify the screen with confidence before acting on it ([REQ-012](#req-012)). [REQ-010](#req-010) needs no threshold: its intro screens are not shown at all. Accepted by Thomas as proposed, 8 November 2026.

<a id="open-g"></a>**OPEN-G — Distribution through F-Droid.** [REQ-028](#req-028). F-Droid builds apps from source and reviews them, which reaches users who avoid unknown APKs, but it requires reproducible builds and an F-Droid metadata entry. **Needed by:** the first release after 1.0. Thomas decided, 8 November 2026, that F-Droid stays a COULD until then.

<a id="open-h"></a>**OPEN-H — Does the website work in landscape?** [REQ-045](#req-045). Whether duolingo.com can be used in landscape in Chrome on the reference device, or asks the learner to rotate back. Thomas checks it by turning the phone during a lesson in Chrome. Raised in the second elicitation pass, 8 November 2026. **Needed by:** implementation of [REQ-045](#req-045).

<a id="open-i"></a>**OPEN-I — Permission for installing updates from the app.** [REQ-041](#req-041). An app that installs APKs needs Android's "install unknown apps" permission, which the learner grants in system settings and which Android warns about. Whether a display tool should ask for it, or should only open the release page so that the browser installs the APK as in [REQ-032](#req-032). Raised in the second elicitation pass, 8 November 2026. **Needed by:** the release that implements [REQ-041](#req-041).

<a id="open-j"></a>**OPEN-J — The report address.** [REQ-033](#req-033). Which address receives emailed reports. It should be a mailbox created for the project, not Thomas's personal address, so that reports stay apart from his own mail and can be handed over. Raised in Thomas's review of v0.3, 8 November 2026. **Needed by:** the release that implements [REQ-033](#req-033).

<a id="open-k"></a>**OPEN-K — How emailed reports become issues.** [REQ-046](#req-046). Candidates: a scheduled GitHub Actions workflow that reads the report mailbox, with its credentials kept as a repository secret, and opens an issue per report (no server); a small serverless function that holds the token and receives mail through a forwarding service (faster, but a service outside GitHub to run and keep safe). Either must drop the sender's address, free text and attachments before publishing. Raised in Thomas's review of v0.3, 8 November 2026. **Needed by:** the release that implements [REQ-046](#req-046).
